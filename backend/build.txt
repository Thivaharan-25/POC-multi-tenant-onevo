Core backend rules:
1. Controllers call services only.
2. Services call repositories only.
3. Repositories call AppDbContext only.
4. Controllers must not inject AppDbContext.
5. Services must not directly use DbSet or raw EF Core queries.
6. Use DTOs for request/response.
7. Use Models for database entities.
8. Use HttpOnly cookie/session auth for tenant users.
9. Do not send access/JWT tokens to frontend.
10. Developer Platform auth can also use HttpOnly cookies for this learning project.
11. Tenant-facing APIs use /api/v1/*.
12. Developer Platform APIs use /admin/v1/*.
13. Developer Platform data must exist, but do not build Developer Platform UI.

Database:
Use PostgreSQL, not SQL Server.

Use package:
- Npgsql.EntityFrameworkCore.PostgreSQL

Connection string in appsettings.Development.json:

"ConnectionStrings": {
  "DefaultConnection": "Host=localhost;Port=5432;Database=onevo_hr_test;Username=postgres;Password=postgres"
}

Register AppDbContext in Program.cs with UseNpgsql.

Use:
- Guid primary keys
- jsonb for payload/snapshot fields where needed
- DateTime UTC values
- indexes on tenant_id, email, status, module_key, feature_key, permission_key

Important product lifecycle:
- Public user books/applies for demo.
- Super Admin approves demo request in Developer Platform.
- Approval creates demo workspace tenant.
- In database, demo workspace tenant status is trial.
- Customer uses demo workspace.
- Customer upgrades/activates from demo.
- Customer gives real company details and confirmed employee count.
- Customer selects allowed paid plan/add-ons and billing cycle.
- Backend creates first invoice.
- Tenant status becomes pending_payment.
- After payment succeeds, tenant becomes active.
- Active tenant gets paid subscription, paid entitlements, resource limits, and setup templates applied.

Correct lifecycle:
DemoRequest -> Trial/Demo Tenant -> Pending Payment -> Active Tenant

Do not model the main demo flow as:
DemoRequest -> Provisioning Draft -> Active

Provisioning status is for operator-created paid drafts only.

Important UserRole scope rule:
- UserRole is for roles manually assigned directly to a user.
- ScopeType and ScopeTargetId are optional manual scope fields.
- These fields must not replace position-derived scope.
- Use them only when manually giving a user a role with a specific scope.

Examples:
- ScopeType null + ScopeTargetId null = no manual scope override.
- ScopeType = department + ScopeTargetId = DepartmentId.
- ScopeType = legal_entity + ScopeTargetId = LegalEntityId.
- ScopeType = tenant + ScopeTargetId null.
- ScopeType = own + ScopeTargetId null.
- ScopeType = direct_reports + ScopeTargetId null.

- TenantId

- RoleId

Rules:
- Roles can be assigned directly to users through UserRole.
- Roles can also be assigned/linked to positions through PositionRoleAssignment.
- Position role assignment is required because position affects access shape.
- Assigning a role to a position is authorization-sensitive.
- For PositionRoleAssignment, scope is derived automatically from org chart, department, legal entity, and position hierarchy.
- For UserRole, manual scope can be stored in ScopeType/ScopeTargetId.

Effective permission source:
- direct user roles
- position-linked roles

Effective scope source:
- direct UserRole manual scope if present
- otherwise position-derived scope
- tenant owner role can resolve to tenant-level scope

11. Scope / RLS Foundation
==================================================

Do not create general manual scope rule tables in this phase.

Scope is derived from:
- active user
- active employee
- active position assignments
- position hierarchy
- department head position
- legal entity
- direct user roles
- position role assignments

Manual scope is allowed only on UserRole:
- UserRole.ScopeType
- UserRole.ScopeTargetId

That is only for manually assigned roles, not normal position-derived access.

Scope levels:
- Own
- DirectReports
- Department
- DepartmentAndChildren
- LegalEntity
- MultiLegalEntity
- Tenant

Create service interfaces:
- ICurrentUserService
- ITenantContextService
- IPermissionService
- IFeatureGateService
- IScopeResolverService

Scope examples:
- Employee role from own position: Own
- Manager position with reports: DirectReports
- Department head: Department
- Top legal entity position: LegalEntity
- User assigned to positions in multiple legal entities: MultiLegalEntity
- Tenant owner role: Tenant
- Direct UserRole with ScopeType = department: that specific department
- Direct UserRole with ScopeType = legal_entity: that specific legal entity

For this learning backend:
- implement RLS-style filtering in services/repositories
- do not implement real PostgreSQL row-level security policies yet
